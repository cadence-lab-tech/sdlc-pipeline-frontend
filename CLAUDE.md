# CLAUDE.md — sdlc-pipeline-frontend

Интерфейс Cadence Lab (Clab): доска задач, карточка задачи с таймлайном и артефактами
по этапам, редакторы ролей и цикла.

## Прежде чем писать код

Домен описан в [sdlc-pipeline-docs](https://github.com/cadence-lab-tech/sdlc-pipeline-docs), локально — соседняя
директория `../docs/`:

- `../docs/ARCHITECTURE.md` — что такое задача, этап, гейт, роль, дрейф
- `../docs/decisions/README.md` — принятые решения

API отдаёт [backend](https://github.com/cadence-lab-tech/sdlc-pipeline-backend); контракт данных совпадает со
схемой в `../backend/migrations/`.

## Стек

Vite, React 19, TypeScript, Tailwind CSS 4 и [shadcn/ui](https://ui.shadcn.com)
на примитивах Radix ([решение 0029](../docs/decisions/0029-shadcn-ui.md)).

## shadcn — как работать

**Компоненты живут в репозитории, а не в node_modules.** `src/components/ui/`
— это исходники, приехавшие командой `npx shadcn@latest add <имя>`; их можно и
нужно править под себя. Обновление библиотеки не перезапишет их само.

```bash
npx shadcn@latest add dialog        # добавить компонент в src/components/ui
npx shadcn@latest add --help        # список доступных
```

Настройки переезда лежат в `components.json`: стиль `radix-nova`, псевдоним
`@/` на `src/`, иконки `lucide-react`.

**Своё поверх готового — в трёх местах, и только в них:**

| Файл | Что там |
|---|---|
| `src/components/kit.tsx` | того, чего в shadcn нет: `Page`, `PageHeader`, `Section`, `Row`/`RowList`, `EmptyState`, `Note`, `StatusDot`, `Token`, `Timestamp`, `CodeBlock`, `Markdown`, `Spinner`, `ConfirmButton` |
| `src/components/fields.tsx` | поля формы: `TextInput`, `TextArea`, `NumberInput`, `Selector`, `MultiSelector`, `Switch`, `FormLayout` |
| `src/components/DataTable.tsx` | таблица с описанием колонок |

**Подпись поля обязана быть связана с контролом** через `label[for]` → `id`.
По этой связке поле находят и программы чтения с экрана, и сквозные сценарии;
`fields.tsx` делает это сам через `useId`, руками `<input>` не верстать.

**Оформление — утилитарными классами Tailwind по токенам темы**
(`bg-background`, `text-muted-foreground`, `border`), а не сырыми цветами.
Цвет, приходящий из данных (`workflow_statuses.color`), — исключение: он идёт
через `style`, потому что его в классах нет.

**Тема светлая и тёмная**, класс `dark` на `<html>` ставит
`src/lib/theme.tsx`; выбор запоминается, «системная» слушает
`prefers-color-scheme`. Любой новый цвет обязан иметь пару для тёмной темы —
проверяется переключателем в шапке.

**Подсказки требуют `TooltipProvider`** — он один на всё приложение, в
`App.tsx`. Radix без него падает, а не деградирует. Там же, и тоже один,
стоит `Toaster` из `components/ui/sonner` — тосты нужны и страницам вне
оболочки.

## Структура

```
src/
  api/         типы по схеме БД, клиент REST, useResource
  components/  общие блоки: гейты, карточка задачи, диалоги, форма свойств
    task/      блоки карточки задачи: действия, детали, этапы, лента
    cycle/     схема цикла задачи: раскладка, состояние на схеме, компонент
    graph/     примитивы графа на SVG и геометрия — общие для схем
    ui/        компоненты shadcn: исходники в репозитории, а не зависимость
  hooks/       useCollapsed, useIsMobile, useInstance (профиль и версия сервера),
               useTaskLevelEditable (право на уровень модели задачи и этапов)
  pages/       Projects, Teams, Principals, Audit, Board, TaskDetail, Roles,
               WorkflowEditor, Knowledge, Metrics, Settings, Login, CLILogin,
               GitHubConnect, Invite
  lib/         cn и провайдер темы
  App.tsx      оболочка с боковым меню, переключатель темы, роутинг
e2e/           сквозные проверки в headless-Chrome поверх живого бэкенда
```

| Страница | Назначение |
|---|---|
| Projects | Проекты и репозитории в их области |
| Teams | Команды: состав и приглашения ссылкой, доступ в проекты, группы провайдера, бюджет по стоимости, опасная зона с удалением организации |
| Principals | Кто заведён в системе; список общесистемный и открыт администратору системы |
| Audit | `/audit`: журнал действий уровня инстанса — записи без проекта (команды, принципалы, токены без проекта, вход CLI); пункт меню «Журнал» по тому же правилу `is_admin`, что «Принципалы» |
| Board | Доска задач по статусам действующего цикла, переключение типа задач, фильтр по эпику, создание задачи |
| TaskDetail | Шапка с ключом и метаданными (ссылки на тикеты основного трекера — только показ), схема цикла задачи над вкладками с выбором этапа в адресе (`?stage=`), этапы с артефактами и арендой, вложенные прогоны перепроверки, нарезка эпика, лента с подробностями событий из `payload`, журнал действий задачи; правая панель — «Действия» (переходы с вердиктом гейтов), «Детали» (статус, тип, приоритет, исполнитель, область с PR, свойства) и сворачиваемые «Связи», «Дрейф», «Стоимость» |
| Roles | Роли и их версии: инструкция, вход, контракт вывода, где роль стоит |
| WorkflowEditor | Версии цикла: черновик под выбранный тип задач, статусы, переходы, гейты, активация |
| Knowledge | Поиск по коду, артефактам и документам плюс состояние индекса по репозиториям |
| Metrics | Длительность статусов, вердикты гейтов, дрейф, стоимость по статусам, ролям и моделям, пропускная способность за период |
| Settings | Участники с уровнями и ролями специалистов, приглашения ссылкой, команды проекта, доступ к GitHub, репозитории в области с отвязкой, токены, экспорт и импорт связки, журнал действий проекта, опасная зона с удалением проекта |
| Login | Вход токеном, через GitHub или через корпоративного провайдера; в режиме header не показывается |
| CLILogin | `/login/cli`: подтверждение входа `clab auth login` по коду из терминала; без входа уводит на Login и возвращается с тем же кодом |
| GitHubConnect | `/settings/github/callback`: возврат от GitHub после установки приложения и повторной авторизации; записывает установку на команду и предлагает репозитории на выбор для проекта |
| Invite | `/invite/:token`: приём приглашения ссылкой — куда зовут, кто, с какой ролью или уровнем и до какого срока; без входа уводит на Login и возвращается на ту же ссылку |

## Конвенции кода

- **Пустые массивы бэкенд опускает** (`omitempty`), поэтому ответы
  нормализуются в `api/client.ts` — один раз на весь клиент. Компонент, который
  сам помнит про «а вдруг поля нет», рано или поздно про это забудет и уронит
  страницу целиком.
- **Данные не кэшируются.** Задачу двигают агенты с других машин; показать
  сохранённый ответ вместо текущего хуже, чем сходить в сеть. При перезапросе
  тех же данных прежний ответ остаётся на экране, чтобы страница не схлопывалась
  в спиннер после каждого действия.
- **Сообщение об ошибке показывается как есть.** Оно уже написано для человека,
  а код ошибки общий у REST и MCP — ветвиться нужно по коду, не по тексту.
- **Необратимое действие — только через `ConfirmButton`** (удаление, отзыв,
  архив, снятие доступа): запрос уходит после подтверждения в `AlertDialog`, а
  в тексте диалога назван объект — ключ, имя или handle. Обратимое («Вернуть
  из архива») подтверждения не просит. Успех — `toast.success` из `sonner` с
  именем объекта, прямо из страницы, без обёрток; тост не заменяет результат
  на экране (выданный токен, отчёт активации остаются на месте). Ошибка —
  `Failure` рядом с формой, как и была; тостов об ошибках нет. Ошибка загрузки
  ресурса получает `reload` и кнопку «Повторить», ошибка действия — нет.
- **Самое дорогое подтверждается вводом ключа.** У `ConfirmButton` есть
  необязательный `confirmPhrase`: в диалоге появляется поле, и пока введённое
  не совпало ровно, кнопка подтверждения выключена; закрытие диалога введённое
  забывает. Так стоят удаление проекта и удаление организации — там, где
  ошибка стоит всего содержимого. Своих диалогов для этого не заводить.
- **Цена удаления называется категориями до, числами после.** Счётчики
  (`removed`) бэкенд считает до удаления, но отдаёт только в ответе:
  ручки-предпросмотра нет. Поэтому диалог перечисляет, что именно исчезнет, а
  числа приходят в тост — `components/removals.ts` собирает их в строку и нули
  не печатает. Выдумывать «0» или «около» до ответа нельзя.
- **Опасная зона стоит отдельно.** Необратимое удаление целого объекта —
  проекта, организации — живёт внизу страницы, за `Separator`, в карточке с
  рамкой и фоном по токену `destructive`, а не дописывается строкой к
  соседнему разделу. У личного аккаунта (`team.kind === 'personal'`) зоны нет:
  он уходит вместе с человеком, и вместо кнопки стоит объяснение. Вид команды
  — данные, а не уровень доступа; по уровню кнопки по-прежнему не прячутся.
- **Категория статуса и вид перехода — перечни схемы**, по ним выбирать
  оформление можно. Ключ статуса и ключ роли придумывает проект — по ним нельзя.
- **Токен живёт в `localStorage` (`sdlc.token`) и добавляется в `api/client.ts`**
  ко всем запросам. Без токена клиент шлёт `X-SDLC-Actor` — это работает только
  в режиме header. Любой 401 поднимает событие `UNAUTHENTICATED_EVENT`, и
  оболочка уводит на `/login`; страницы про аутентификацию не знают. Права
  проверяет бэкенд: 403 показывается как обычная ошибка, кнопки по уровню
  участника не прячутся ([решение 0021](../docs/decisions/0021-token-auth-and-project-members.md)).
- **Вход через провайдера не заводит второго транспорта.** Браузер проходит
  код авторизации с PKCE (клиент публичный, секрета у него нет и быть не
  может), меняет код на ID-токен у самого провайдера и отдаёт токен бэкенду;
  тот проверяет подпись, издателя и аудиторию и возвращает обычную сессию —
  дальше всё работает как с любым другим токеном
  ([решение 0027](../docs/decisions/0027-teams-and-oidc.md)). Проверять
  ID-токен в браузере бессмысленно: «кто пришёл» решает сервер. Вход через
  GitHub устроен так же, только без PKCE: код приходит на `/login/github`,
  браузер сверяет `state` и отдаёт код бэкенду — секрет клиента живёт там
  ([решение 0030](../docs/decisions/0030-member-roles-github-login-open-projects.md)).
- **Выход отзывает сессию на бэкенде,** а не только забывает токен в браузере:
  забытый токен остался бы действующим.
- **GitHub подключается двумя переходами, и оба начинает браузер**
  ([решение 0034](../docs/decisions/0034-github-installation-on-tenant.md)):
  `api/github.ts` хранит намерение (команда, проект, `state`) в
  `sessionStorage`, уводит на страницу установки приложения, а с возврата на
  `/settings/github/callback` — за кодом повторной авторизации на тот же
  адрес. Код отдаётся бэкенду один раз; репозитории на выбор — то, что
  бэкенд вернул, интерфейс их не выдумывает и токенов GitHub не видит.
- **Вход CLI подтверждается здесь, а не в CLI.** `clab auth login` показывает
  код и открывает `/login/cli?code=…`; страница спрашивает бэкенд, что за
  запрос, и по кнопке выдаёт той машине долгоживущий токен от имени вошедшего
  ([решение 0032](../docs/decisions/0032-cli-login-device-flow.md)). Сам токен
  через браузер не проходит: его получает CLI при опросе.
- **Ссылка-приглашение показывается один раз** (решение 0035). Токен
  `clab_inv_…` приходит только в ответе на выдачу; интерфейс собирает из него
  `window.location.origin + '/invite/' + токен` и держит в состоянии открытого
  диалога — не в `localStorage`/`sessionStorage`, не в адресе и не в списке.
  Закрыли диалог — ссылка забыта: в базе лежит хеш, второй раз её не
  показать, потерянную отзывают и выдают новую. Срок, допустимые роли и отказ
  личному аккаунту решает бэкенд; кнопка «Пригласить» не прячется нигде,
  включая личный аккаунт, — диалог показывает сообщение бэкенда.
- **Приглашение принимается на странице вне оболочки, как вход CLI**
  (решение 0035): у только что вошедшего нет ни одного проекта, а без входа
  `/invite/:token` уводит на Login и возвращается на ту же ссылку. Токен
  приглашения ходит только в теле `POST /invites/lookup` и `/invites/accept`,
  а не в пути или query API: пути оседают в логах, а ссылка — пропуск на
  предъявителя; в хранилище браузера он не пишется. `role_keys: null` у
  приглашения — «любые роли» и в `[]` не превращается. Ошибка приёма
  ветвится по коду: `conflict` и `not_found` окончательны, остальное
  (квота приходит как `forbidden`) можно повторить.
- **Аренда лежит на прогоне этапа, а не на задаче.** Кто держит работу, видно
  из `stage_runs.claimed_by_handle` и `lease_expires_at`; доска берёт это из
  очереди проекта (`GET /projects/{key}/queue`), потому что в списке задач
  аренды нет. Истёкшая аренда показывается истёкшей, а не пустой: разница
  объясняет, почему задача стоит.
- **Пока аренда жива, карточка перезапрашивает себя** раз в десять секунд:
  за ней стоит агент на другой машине, и о его работе страница узнаёт только
  перезапросом. Аренда кончилась — опрос прекращается.
- **Перепроверка — вложенный прогон, а не отдельный этап**
  ([решение 0017](../docs/decisions/0017-review-as-nested-stage-run.md)):
  она рисуется внутри своего родителя по `parent_run_id`, а не отдельной
  карточкой рядом.
- **Панель карточки задачи отвечает на «что сейчас можно сделать».** Первым
  блоком идут «Действия»: доступные переходы кнопками, у закрытых — счётчик
  держащих гейтов и список под `Collapsible`. Вердикт по-прежнему считает
  бэкенд; счётчик — подсчёт уже полученных статусов, а не своя проверка.
- **Настройки вида живут в `localStorage`, данные — нет.** Свёрнутость секций
  панели помнит `hooks/useCollapsed` под общим ключом на все карточки: это про
  то, как человек читает экран, а не про состояние задачи, и конвенцию «данные
  не кэшируются» не нарушает.
- **Подписи перечней схемы — словарь с запасным вариантом.** Типы событий
  (`components/task/events.ts`) и приоритеты (`components/priorities.ts`)
  подписаны по-русски, но незнакомый ключ показывается как есть: событие
  заводится на бэкенде раньше, чем подпись здесь, и лента от этого падать не
  должна. Ключи статусов и ролей так подписывать нельзя — их придумывает
  проект.
- **Лента — что случилось с задачей, журнал — кто что вызывал** (CLAB-211).
  Лента читает доменные события (`task_events`), журнал — записи вызовов
  MCP и REST с токеном, каналом и исходом, включая отказы (CLAB-210); одно в
  другое не сливается. Подробности события — строка из `payload` по
  правилам `eventDetails` в `components/task/events.ts`: ключи статусов и
  ролей как пришли, незнакомый тип и неполный `payload` — пустая строка, а
  сырой `payload` доступен по раскрытию у любого события.
- **Журнал грузится по открытию, а не вместе с карточкой.** Отказ `403` на
  чтении журнала сам становится записью журнала, и карточка, открытая
  наблюдателем, не должна оставлять такую запись при каждом показе. Поэтому
  `AuditLog` монтируется только во вкладке «Журнал» (в настройках проекта и на
  `/audit` — вместе со страницей) и перезапрашивается по знаку `version`:
  действие на карточке и опрос живой аренды сбрасывают его к первой странице,
  прежний ответ остаётся на экране до нового. Пагинация — курсором `next`
  («Показать ещё»). Вид токена, канал и исход подписывает
  `components/audit.ts` — словарь с запасным вариантом: незнакомый вид
  токена показывается ключом, токен задачи (`task`, CLAB-212) выделен цветом.
- **Оболочка держит сводку проекта, страницы — свои данные** (CLAB-79).
  `Shell` в `App.tsx` спрашивает `GET /projects/{key}/health` при входе на
  страницу проекта, на каждом переходе между его страницами и по событию
  `PROJECT_HEALTH_EVENT` (его шлёт страница, узнавшая о приложении что-то
  новее, — кнопка «Проверить доступ»); таймера нет. Из сводки берутся только
  отметки в боковом меню: у «Настроек» — ключ приложения GitHub не принят, у
  «Поиска» — есть нечитаемые репозитории. Сводка вспомогательная: страница её
  не ждёт, а её отказ (нет ручки у старого бэкенда, 403, сбой) на экран не
  выводится — отметок просто нет. Подробности по-прежнему запрашивают сами
  страницы своими ручками; тянуть их из сводки нельзя — в ней нет ни текста
  провайдера, ни строк индекса, и видит её любой участник. Правила «что
  сказать» про приложение, установки, прогон и отметки — в
  `components/health.ts`, без разметки, и проверяются в `e2e/labels.mjs`;
  `e2e/health.mjs` сверяет экран с тем, что отдал бэкенд стенда, и о
  состоянии стенда ничего не предполагает. Поля `app` и `failure`
  необязательные: бэкенд старше интерфейса их не отдаёт, и экраны тогда
  выглядят как раньше.
- **Уровень модели — ползунок, а не строка модели** (решение 0060, CLAB-262).
  Один компонент `ModelLevelToggle` («авто», low, medium, high) стоит в
  «Деталях» задачи и в форме версии роли; «авто» — отсутствие уровня, в
  запросе `""`. Подписи, строка прогона «рекомендован · фактически» и право
  правки — `components/modelLevel.ts`, без разметки, проверяются в
  `e2e/labels.mjs`. Это единственное место, где интерфейс сам выключает
  контрол по уровню доступа: ползунок задачи только для чтения, если
  интерфейс знает, что maintainer у человека нет (причина — во всплывающей
  подсказке, отдельной строки на экране нет); не знает — доступен, и
  отказ показывает сервер. `model_hint` устарел: на экране его нет, форма
  версии переносит значение базовой как есть. Уровень этапа — тот же
  ползунок в панели выбранного этапа (CLAB-285): пишет `stage_settings`
  задачи по ключу статуса, стоит только у статуса с ролью-исполнителем.
  Право у обоих ползунков одно — `hooks/useTaskLevelEditable`, который
  страница зовёт один раз и раздаёт «Деталям» и панели.
- **Уровень команды — не отдельные права, а тот же уровень проекта.**
  Действующий уровень человека — максимум из путей: поимённое участие, участие
  команды и владение проектом. Считает его бэкенд, интерфейс показывает.
- **Профиль инстанса — из `GET /v1/instance`, один запрос на загрузку**
  (CLAB-89). `hooks/useInstance` держит ответ на уровне модуля, общим для
  оболочки и страницы входа; 404 или сбой — профиль `shared` без версии.
  Ветвиться по профилю — только по `tenancy` (`isSingle`), не по виду команд
  и не по `is_admin`. В `single` нет самообслуживания общего инстанса:
  «Завести команду» только у администратора, ни групп «Личный аккаунт /
  Организации», ни «Тарифа», ни превращения в организацию, а форма проекта
  требует команду. Раздел «Тариф» рисуется только при `plan` в ответе — в
  `single` бэкенд его не отдаёт. Версия сервера стоит в подвале меню, а
  команды установки и входа CLI на странице входа строятся правилами
  `components/cli.ts` (версия выпуска — как `parseRelease` в CLI).

- **Схема цикла — версия задачи, раскладка — чистая функция** (CLAB-284).
  Карточка грузит версию цикла задачи (`task.workflow_id`) одним запросом на
  схему и «Действия»; версия иммутабельна, опрос живой аренды её не
  перезапрашивает. `components/cycle/layout.ts` раскладывает статусы по кругу
  в порядке `position` без React: соседи по кругу — дугой снаружи, возвраты
  (`kind = reject`) и переходы через статус — внутри, возврат пунктиром,
  переход «из любого статуса» — одно обозначение у целевого узла.
  `components/cycle/state.ts` — текущий, пройденный, будущий, попытки
  верхнего уровня и «ждёт апрува» по уже полученным прогонам и вердикту
  гейтов. Ключей статусов и ролей в обоих модулях нет — это проверяет
  `e2e/cycle-layout.mjs`. Примитивы (`components/graph/`: холст, узел, ребро,
  вход «откуда угодно», значок) — SVG своими руками, без библиотеки и без
  предметной области: их же возьмёт граф эпика. Выбор этапа — `?stage=` в
  адресе с записью в историю; незнакомый ключ — как без выбора; выбор
  открывает во вкладке «Этапы и артефакты» панель этапа. На узком экране (`useIsMobile`)
  вместо круга — степпер с теми же узлами. Опоры сценариев — `data-cycle-*`;
  `data-stage-run` и триггеров `Collapsible` у узлов нет.

- **Панель выбранного этапа читает карточку, а не считает сама** (CLAB-285).
  По `?stage=` вместо списка всех прогонов — попытки статуса верхнего уровня
  (новые сверху, последняя раскрыта) с ролью и версией, перепроверками,
  вердиктами гейтов из `gate_results` (как записаны, без пересчёта),
  возвратом с обеих сторон (`exit` и `rejected_from_run_id`), стоимостью
  прогона и итогом этапа, где прогоны без отчёта считаются числом, а не
  нулём; ниже — события статуса из `timeline?status=` строкой ленты. Статус
  без прогонов — роль и выходы по версии цикла. Правила — в
  `components/task/stagePanel.ts` без React, проверяются `e2e/stage-panel.mjs`
  без браузера. Ленту этапа держит страница и перезапрашивает её вместе с
  карточкой, в том числе опросом живой аренды. Опоры сценариев —
  `data-stage-panel`, `data-run-id`, `data-return`, `data-gate-verdict`,
  `data-run-cost`, `data-stage-total`, `data-stage-events`,
  `data-stage-unstarted`, `data-stage-model-level`.

## Что нельзя делать

- **Хардкодить статусы и роли.** Они кастомные на каждый проект и приходят из
  API. Никаких списков `['analysis', 'development', …]` в коде и никаких цветов,
  привязанных к именам статусов — цвет лежит в `workflow_statuses.color`.
- **Считать набор гейтов фиксированным.** Типов десять, конфиг у каждого свой;
  UI рендерит по типу, а не по позиции.
- **Считать, что цикл в проекте один.** Активных циклов столько, сколько типов
  задач, и доска показывает один из них ([решение 0024](../docs/decisions/0024-epic-as-task-with-own-workflow.md)).
  Тип берётся из `active_workflows`, а не из списка в коде: `task` и `epic` —
  данные проекта, а не перечисление фронтенда.
- **Показывать «нет отчёта» как ноль.** Прогон, о котором агент не отчитался,
  стоит «неизвестно»; в карточке и метриках такие прогоны считаются отдельно
  ([решение 0026](../docs/decisions/0026-usage-per-stage-run.md)), и сложить их
  с настоящими нулями значит соврать о счёте.
- **Дублировать доменные правила.** Проверку «можно ли перейти» делает бэкенд;
  фронтенд показывает результат `check_gates`, а не считает его сам.
- **Считать задачу однорепозиторной.** У задачи есть свойства
  (`tasks.properties`) и область по репозиториям (`task_repositories`). Карточка
  рендерит форму свойств по определениям из API (`task_property_defs`), а не по
  захардкоженному списку полей, и показывает область как набор репозиториев —
  для мультирепозиторной задачи их несколько, с PR и сигналами дрейфа на каждый.
- **Двигать задачу перетаскиванием карточки.** Колонка — это статус, а между
  статусами задачу переводит именованный переход со своими гейтами; в одну и ту
  же колонку ведут разные переходы («сдать» и «вернуть»), и у них разный смысл.
- **Раскладывать задачи по доске по `status_id`.** Задача, начатая на прежней
  версии цикла, доходит по ней, и у её статуса другой идентификатор — раскладка
  идёт по `status_key`. Задача со статусом, которого в действующей версии уже
  нет, попадает в отдельную колонку, а не пропадает.
- **Править активный цикл.** Редактируется только черновик; активная версия
  открыта на чтение, и это видно на экране.

## Проверки

`npm run typecheck`, `npm run lint`, `npm run build` и `npm run e2e`.

Сквозные проверки (`e2e/`) кликают настоящими кнопками в headless-Chrome поверх
поднятого бэкенда: экраны показывают вердикт гейтов и состояние цикла, и
подменять их заглушками — значит проверять заглушки. Подтверждение в
`[role=alertdialog]` делает помощник `confirm(текст)` из `e2e/driver.mjs`;
`texts()` вычитает тосты из текста страницы, сами тосты читает `toasts()`.
Порядок сценариев значим:
`labels.mjs` идёт первым и браузера не требует — он проверяет словари подписей
прямо в исходниках (node читает `.ts` сам), включая запасной вариант для
неизвестного ключа, и правила `components/health.ts` на всех состояниях
приложения GitHub сразу. `health.mjs` идёт после `settings.mjs` и сверяет
меню, настройки и состояние индекса с ответами бэкенда этого стенда. `workflow.mjs` активирует новую версию цикла, `epic.mjs`
рассчитывает на демонстрационный эпик с тремя нетронутыми детьми, а
`knowledge.mjs` идёт после
`task.mjs`, потому что аренду берут на прогоне аналитики SDLC-1, который до
того ещё не начат. Отказ движка и вторую попытку этапа `task.mjs` разыгрывает
на SDLC-2, а не на SDLC-1: состояния ставятся ручками API (снятие гейтов
решением, переход от лица другого актора, возврат), потому что кликом их не
добиться, а SDLC-1 нужна следующим сценариям нетронутой. `invite.mjs` идёт последним: приём приглашений добавляет
участников в SDLC, а второй человек в нём — актор заголовка.
Удаление сценарии проверяют только на том, что завели сами: `settings.mjs`
заводит проект `DELME` и удаляет его, `admin.mjs` последним шагом удаляет свою
организацию `e2e-team`. Демонстрационный проект не удаляется никогда — на нём
проверяется отказ: отвязать репозиторий, стоящий в области живой задачи,
бэкенд не даёт. Вход через провайдера и GitHub
сценариями не покрыт: для него нужен живой IdP, а обмен и подписи проверяет
бэкенд — там это и проверяется. База поднимается заново
(`cd ../backend && make reset && make up`) — сиды не идемпотентны.

`model-level.mjs` (CLAB-262) тоже заводит свою задачу и свои роли (ключи с
отметкой времени) и повторяется на той же базе; идёт сразу после
`audit.mjs`. Отказ правки уровня и уровень доступа подменяются ответом одной
ручки, снимок уровня и учёт прогона — настоящие: этап забирает агент, а
отчёт о стоимости шлёт ручкой API.

`audit.mjs` (CLAB-211) заводит себе свою задачу и всё делает с ней ручками
API, поэтому демонстрационных задач не трогает; идёт после `health.mjs` и до
`workflow.mjs` — переходы у него демонстрационного цикла. Стенд в режиме
header отказа 403 не отдаёт: отказ чтения журнала и признак `is_admin`
подменяются в браузере ответом одной ручки (`addInitScript`), а неуспех «по
делу» — настоящий `409` гейтов.

Схему цикла (CLAB-284) проверяют три сценария. `cycle-layout.mjs` идёт
сразу за `labels.mjs` и браузера не требует: раскладка и правила состояния
на записанных циклах нашего проекта, синтетических графах и всех версиях
циклов стенда, плюс поиск ключей статусов и ролей в модулях схемы. Модули
интерфейса импортируют друг друга без расширения, и сценарий подставляет
`.ts` хуком `registerHooks`. `cycle.mjs` заводит свою задачу и двигает её
ручками API (старт, снятие гейтов, апрув, переход, возврат, аренда агента);
идёт после `model-level.mjs` и до `workflow.mjs`; Tab нажимает настоящей
клавишей (`s.key` драйвера), иначе `:focus-visible` не включается, а тему
ставит явно — «системная» в headless-Chrome следует за машиной.
`cycle-version.mjs` идёт сразу после `workflow.mjs`: начатая задача
показывает прежнюю версию, задача из бэклога — новую.

Панель этапа (CLAB-285): правила — `stage-panel.mjs` сразу за
`cycle-layout.mjs`, без браузера; экран — последний раздел `task.mjs` на
своей задаче, проведённой ручками API через перепроверку, апрув и возврат
с описанием проблемы, вместе с опросом живой аренды и обеими темами
(`SDLC_E2E_SHOTS=<каталог>` — снимки панели в PNG, `s.screenshot()`
драйвера); ползунок уровня этапа — раздел `model-level.mjs` на второй своей
задаче.

`instance.mjs` идёт в общем прогоне сразу после входа: правила
`components/cli.ts` проверяет без браузера, а 404, сбой и выпускную версию
`/v1/instance` подменяет в браузере ответом одной ручки
(`addInitScript` драйвера). `single.mjs` в `run.sh` не входит: ему нужен
стенд с `SDLC_TENANCY=single`, `SDLC_AUTH_MODE=token` и `SDLC_ADMIN_TOKEN`
на свежей базе, запуск — `SDLC_ADMIN_TOKEN=<тот же секрет> node
e2e/single.mjs` при поднятом headless-Chrome. «Человек без команды» и лид
там — агенты с токенами от администратора: человека заранее не завести.

## Верстак задачи

Файлы задачи правятся в рабочей копии `.worktrees/<ключ>/frontend` на хосте,
а проверяются в верстаке стека задачи — контейнере `node:24-bookworm` с
примонтированной копией
([решение 0041](../docs/decisions/0041-task-toolbox-in-compose.md)). Порядок
целиком — `../docs/PROCESS.md`, раздел «Верстак задачи»; устройство —
`../backend/dev/README.md`, «Верстаки задачи».

- Стек поднимается из копии backend задачи (`dev/stack.sh up <ключ>`), и
  копию фронтенда он берёт соседнюю: `.worktrees/<ключ>/frontend`. Задача
  только по фронтенду — из основной копии backend с явным путём:
  `../backend/dev/stack.sh up <ключ> --frontend <эта копия>`.
- Внутри: `../backend/dev/stack.sh exec <ключ> frontend npm run typecheck`,
  так же `npm run lint`, `npm run build`, `node e2e/labels.mjs`.
  Зависимости ставятся сами при первом `exec` и после смены
  `package-lock.json` — в том стека, не в копию; `npm install` внутри не
  запускать, новая зависимость — правка `package.json` и `npm install` на
  хосте в копии, после чего верстак подхватит lock-файл.
- `npm run e2e` и просмотр экранов — на хосте: им нужны headless-Chrome и
  живой бэкенд. Интерфейс — `SDLC_API_URL=<адрес стека> SDLC_UI_PORT=<порт>
  npm run dev` в копии, для этого в ней свой `npm ci` под macOS; `node_modules`
  копии и верстака не пересекаются.
- git внутри верстака не работает: ветка, коммиты и push — на хосте.
- Общие точки, где сходятся параллельные задачи, — роутер, навигация,
  словари подписей, общие компоненты `components/ui/`. Кто ещё правит
  фронтенд на этой машине — `git worktree list` здесь, что именно —
  `git diff --stat origin/main...<ветка соседа>`; правь такие места точечно.

## Статус

Интерфейс переведён с Astryx на shadcn/ui
([решение 0029](../docs/decisions/0029-shadcn-ui.md)): экраны и навигация те
же, поменялись компоненты, появились тёмная тема и сворачиваемое боковое меню.

Фазы 1, 4, 5 и 6 закрыты: доска с переключением типа задач и фильтром по эпику,
карточка задачи с нарезкой, стоимостью, связями и назначением исполнителя,
редактор ролей и цикла с типами задач у черновика, вход по токену и через
корпоративного провайдера, участники и токены проекта, команды с бюджетами и
группами провайдера, доступ к GitHub у проекта с проверкой по кнопке, перенос
связки правил, метрики цикла вместе со стоимостью.

Выход к коллегам (решение 0030): вход через GitHub, роли специалистов у
участников и команд проекта в настройках, создание проекта со страницы
проектов тем, кому бэкенд это разрешает (`can_create_projects`).
Страница подтверждения входа CLI (решение 0032).

Удаление из интерфейса: отвязка репозитория и удаление проекта в настройках,
удаление организации на странице команд — каждое через диалог, у проекта и
организации с вводом ключа. Архивации команды нет: `archived_at` никем не
проставляется, и жетон с кнопкой убраны. Удаление арендатора делается только
отсюда — ни в CLI, ни в MCP его нет.

Приглашения ссылкой (решение 0035): выдача с уровнем, ролями специалистов и
сроком, список со статусами и отзыв — в участниках проекта и в составе
команды; у личного аккаунта выдачу отклоняет бэкенд, и диалог показывает его
сообщение.

Карточка задачи переложена под чтение: панель «Действия» → «Детали» →
сворачиваемые секции, липкая на широком экране, шапка с копированием ключа и
русским приоритетом, лента с человеческими подписями событий по дням, у этапов
раскрыта последняя попытка.

Долги интерфейса закрыты: аренда прогона с живым перезапросом карточки,
вложенные прогоны перепроверки, сигналы дрейфа с разбором прямо из карточки,
состояние индекса и поиск по знанию проекта.

Вложенные прогоны перепроверки покрывает панель этапа в `task.mjs`: гейт
`agent_review` там запускает запрос перехода, а перепроверку забирает
второй агент ручками API. Остальное покрыто —
`e2e/knowledge.mjs` берёт аренду настоящим агентом через API и проверяет, что
экран её показывает.
