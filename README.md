# SDLC Pipeline — Frontend

Интерфейс системы, ведущей задачи по настраиваемому циклу разработки: доска
задач, карточка задачи с таймлайном и артефактами по этапам, редактор ролей и
редактор цикла с гейтами.

Бэкенд: [sdlc-pipeline-backend](https://github.com/stepaKaziatko/sdlc-pipeline-backend) ·
Документация по домену: [sdlc-pipeline-docs](https://github.com/stepaKaziatko/sdlc-pipeline-docs)

## Стек

Vite, React 19, TypeScript, Tailwind CSS 4 и
[shadcn/ui](https://ui.shadcn.com) на примитивах Radix.

Компоненты shadcn лежат в `src/components/ui/` исходниками, а не приезжают
зависимостью: их правят под себя, а новые добавляют командой
`npx shadcn@latest add <имя>`. Тема светлая и тёмная, переключатель — в шапке.

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173, /v1 проксируется на бэкенд
```

Бэкенд поднимается отдельно (`cd ../backend && make up`) на `localhost:8088`;
адрес переопределяется переменной `SDLC_API_URL`.

Вход зависит от режима бэкенда. При `SDLC_AUTH_MODE=header` действующее лицо
уезжает в заголовке `X-SDLC-Actor` (по умолчанию `web`, хранится в
`localStorage`) и права не проверяются — это режим отладки цикла. При
`SDLC_AUTH_MODE=token` нужен токен: его вводят на странице входа или получают
входом через корпоративного провайдера, если тот настроен
(`SDLC_OIDC_ISSUER`). Вход через провайдера идёт кодом авторизации с PKCE, а
ID-токен меняется на обычную сессию бэкенда — второго транспорта у системы
нет.

```bash
npm run typecheck
npm run lint
npm run build
npm run e2e      # сквозные проверки в headless-Chrome поверх живого бэкенда
```

## Страницы

| Страница | Назначение |
|---|---|
| Projects | Список проектов, репозитории в области проекта |
| Teams | Команды: состав, доступ в проекты, группы провайдера, бюджет |
| Principals | Кто заведён в системе; видна администратору системы |
| Board | Доска задач по статусам действующего цикла, создание задачи |
| TaskDetail | Этапы с артефактами, вердикт гейтов, переходы, область и свойства, лента |
| Roles | Роли и их версии: инструкция, вход, контракт вывода, где роль стоит |
| WorkflowEditor | Версии цикла: черновик, статусы, переходы, гейты, проверка, активация |
| Metrics | Длительность статусов, вердикты гейтов, дрейф, стоимость, пропускная способность |
| Settings | Участники с ролями специалистов, команды проекта, доступ к GitHub, токены, перенос связки |
| Login | Вход токеном, через GitHub или через корпоративного провайдера |

## Что интерфейс не делает

- **Не считает, можно ли перейти.** Вердикт по каждому гейту приходит из API;
  экран его показывает и даёт закрыть то, что закрывает человек.
- **Не двигает задачу перетаскиванием карточек.** Между статусами задачу
  переводит именованный переход со своими гейтами, и в одну колонку могут
  вести разные переходы — «сдать» и «вернуть».
- **Не решает, кому что можно.** Права проверяет бэкенд: 403 показывается как
  обычная ошибка, а кнопки по уровню участника не прячутся. Исключение одно —
  список принципалов: он общесистемный и лиду команды не отдаётся вовсе.
- **Не проверяет ID-токен провайдера.** Браузер получает его кодом
  авторизации и отдаёт бэкенду; подпись, издателя и аудиторию проверяет тот.
  Код от GitHub браузер тоже только передаёт: секрет клиента живёт на бэкенде.
- **Не правит активный цикл.** Правка — черновик, который активируется целиком
  ([решение 0016](https://github.com/stepaKaziatko/sdlc-pipeline-docs/blob/main/decisions/0016-workflow-versions-immutable.md)).

## Статус

Закрыты фазы 1, 4, 5 и 6: доска с переключением типа задач, карточка задачи с
нарезкой эпика, стоимостью и назначением, редакторы ролей и цикла, метрики,
вход и права, перенос связки, команды с бюджетами, вход через корпоративного
провайдера и настройка доступа к GitHub у проекта. Сквозные проверки проходят.

Выход к коллегам ([решение 0030](https://github.com/stepaKaziatko/sdlc-pipeline-docs/blob/main/decisions/0030-member-roles-github-login-open-projects.md)):
вход через GitHub, роли специалистов у участников и команд проекта, создание
проекта со страницы проектов.

Не сделано: аренды и живой прогресс агента, вложенные прогоны перепроверки
(фаза 2), сигналы дрейфа, состояние индекса и поиск (фаза 3) — REST всё это
уже отдаёт.
